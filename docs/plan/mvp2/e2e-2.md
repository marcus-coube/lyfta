# Roteiro E2E — MVP 2.0

Roteiro do passo 1 da P8.4: do ajuste do fuso da organização à reativação de um
aluno, passando por modelo com superset, execução offline, financeiro com baixa
manual e dashboard. Segue o modelo do [e2e-final.md](../mvp1/e2e-final.md) e
estende o [e2e-p1.md](../mvp1/e2e-p1.md) (o treino offline segue valendo como
sub-roteiro). A regressão do 1.0 é o próprio e2e-final, repetido ao fim (seção
"Regressão do 1.0").

Um passo que falha interrompe o roteiro: anotar o bug nas Notas da P8.
**Regra do registro:** `✅` só quando o passo foi **executado de verdade** e o
resultado esperado aconteceu; `⚠️` quando só parte foi exercitada (ex.: backend
sim, tela não); `⬜` quando não foi executado. O motivo de todo `⚠️`/`⬜` vai na
tabela de observações.

## Pré-requisitos

| Item | Como |
|---|---|
| Bancos | `psql -U postgres -f backend/scripts/create-dbs.sql` (5 bancos, inclui `lyfta_billing`) |
| Redis + MinIO | `cd backend && docker compose up -d` |
| Seed da biblioteca | `psql -U postgres -d lyfta_workout -f backend/workout/seed/exercises_seed.sql` |
| 5 serviços no ar | identity 8081, workout 8082, assessment 8083, comms 8084, billing 8085 (`go run ./cmd/api` em cada, com `.env`) |
| Convite | em dev o `logMailer` imprime o link no log do `identity` (o token está na URL) |
| Owner e coach | Chrome (`flutter run -d chrome` ou `app/build/web` servido); coach numa janela anônima |
| Alunos | aluno 1 no emulador Android (`--dart-define` apontando `10.0.2.2` para os **5** serviços; ver app/README.md); aluno 2 em Chrome anônimo (ou iOS) |
| Relógio do job | o job do billing varre na subida e a cada 15 min. Para **forçar o tick**: reiniciar o `billing` (varre ao subir). Para **vencer** uma fatura: `UPDATE invoices SET due_date = current_date - 1 WHERE id = '<id>'` no `lyfta_billing` como superusuário e reiniciar o `billing` |
| Push | fora do roteiro (pré-loja L1/L3) |

Dados usados abaixo: owner `owner@e2e2.test`, coach `coach@e2e2.test`, aluno 1
`aluno1@e2e2.test`, aluno 2 `aluno2@e2e2.test`.

|---|---|

Uma correção digitada errada (5.255,5 kg) foi rejeitada no sync e descartada pela fila (regra do ADR-003: rejeitado sai da fila); a correção seguinte (55 kg), que revisa a rejeitada, caiu como `unknown_revised_log`. | **A10** (aguarda decisão) | **Login aparece ao abrir com sessão salva.** Enquanto o refresh da sessão guardada roda (status `unknown`), o redirect do `app_router` trata como deslogado e mostra o formulário de login por alguns segundos antes de ir ao Hoje. ### Falha encontrada e corrigida

  `TenantRepo.ListAfter` limitava a `MaxTenantPageSize` (500) e cortava a linha

  `next_cursor`. Com 1.637 tenants no banco de dev, o tenant do roteiro ficava de
  fora dos jobs do billing (geração e vencimento) e do comms (treino pendente).
  Em produção seria silencioso a partir do 501º tenant. Corrigido no commit
  `fix(p8.4)` com teste que falha sem a correção. Depois do conserto o job
  recriou a fatura e venceu a do aluno 3 no mesmo tick.
